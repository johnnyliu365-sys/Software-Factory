## Why

Wave 3 made the gates real at the level of one ticket: dispatch lint, evidence gate, usage report, integration script. Around a ticket, the harness still relies on an agent reading rules and following them:

- **Where the documents live, and how they get there.** In a new project an agent copies them from the template; in a mature project it should reuse the project's own paths; in a half-built project old and new copies are mixed. Nothing checks which case applies.
- **Indexes are not pinned.** `index_pins.py` exists, but no index in a target project carries its pin format, no hook runs it, and CI does not run it.
- **A user who is not an engineer cannot see where the mechanism failed.** On 2026-11-20 the owner saw Codex, with the 0.4.14 plugin installed, answer a plain lookup by reading `Workflow.md` and the whole governance chain. The owner saw it because the owner designed the harness; a lay user sees only slowness or odd behaviour. Ticket 79 fixes the entry for 0.5.0. Copies of `AGENTS.md` and `Workflow.md` already in target projects keep the old rule.
- **Agile coupling outlives the POC.** The harness allows a fast, agile POC, but nothing stops the coupling of a POC from becoming the architecture of the product. Module boundaries exist only as an architecture document; no gate compares the code with them. The language policy fixes one backend language but does not require the choice to be made against the project's needs, nor its trade-offs and technical debt to be stated before the choice.

## Themes

| # | Theme | What it delivers |
| --- | --- | --- |
| T1 | Project-type survey and mapping | A program surveys the document tree and writes a versioned survey record. For each standard source (CONTEXT, PRD, requirements, SPEC, tickets, reviews, ADR, handoffs, state files) the record holds the path, missing or in conflict. The project type (new, mature, half-built) follows from signals in that record, not from an agent's impression. A mature or half-built project gets a versioned mapping table (standard source → this project's path), and every later check and hook finds files through it. Each type sets its baseline: empty for a new project, the surveyed state for the other two. The classification states its evidence and a confidence level. A mature project can have no governance documents at all, so structure alone does not decide. When the evidence is insufficient, the type is `PENDING_OWNER`; the owner decides, and until then no document is created and no structural repair is applied. |
| T2 | Old copies of the plugin's rules | The copies of `AGENTS.md` and `Workflow.md` a project holds carry a version marker. At the start of a session the entry compares them with the installed plugin, and reports an older copy with the way to update it instead of following it. |
| T3 | Index pins and the hook loop | Target-project indexes use the pin format of `index_pins.py`, kept by `--write`. A post-edit hook runs `--check` when a leaf or an index under the mapped paths changes, and a pre-commit hook blocks drift. Both find their scripts and files from the project root the host passes (`CLAUDE_PROJECT_DIR`), never the working directory, and block only the action they check (L-23 addendum of 2026-11-19). A digest over a fenced block fails on an unclosed fence, and a digest that did not change after its content changed is flagged (2026-11-19 lesson). CI runs the same checks as the backstop. **Limits stated:** the plugin installs no git hook in a target project, and CI checks only when it runs. T3 proves integrity, meaning that controlled content has not changed without approval. It does not prove that the content is correct or that an agent understood the requirement; that is the work of independent review and behaviour gates. A pin baseline edited together with its leaf would make the check agree with itself, so every change of a pin value must trace to an approval record (a ticket or a change record), and CI checks the history for pin changes without one. A preflight sweep clears the stale residue of a seat that has ended, judged by run id and age, and records it (external review, 2026-11-19). |
| T4 | Self-diagnosis in plain language | A health-check command, run by the user or at session start, reports in fixed plain-language form what is wrong, what it means and what to do. It covers the survey state, old copies, pin drift, stuck tickets and the last halt. Every halt code has a shipped plain-language entry (L-16). A hook records which files an agent read, and flags a behaviour that breaks the routing, for example a read-only lookup that read `Workflow.md` or many governance files. |
| T5 | Module boundaries after the POC | The POC may be agile. To leave the POC, two things are required: a module boundary map (each module's responsibility, public interface and allowed dependencies) and a technical-debt inventory of the POC's couplings, kept in the per-feature record of existing design and known debt (L-21). From MVP on, a dependency-rule gate compares the real import graph with the map at every integration. A new forbidden edge or a cycle is red, and fan-in and fan-out are reported. |
| T6 | Technology choice with its trade-offs stated | Before the POC ends, architecture produces a decision record that compares candidate backend languages and frameworks against the project's needs. The needs it covers are target users and scale, traffic and latency, front-end responsiveness, deployment and running cost, and team maintainability. The record states each option's strengths, weaknesses and the technical debt it brings. The owner approves it, and the choice is then fixed; a later change goes through change control. The language gate becomes mandatory from MVP on, instead of at a stage the target project picks. |
| T7 | The user's own edits: detect, classify, restore | Hooks see only an agent's actions. A user who edits, moves or deletes a governance file in an editor bypasses them, and the plugin may not become a target-project git hook. The session-start health check (T4) therefore compares the index pins (T3) with the tree, lists uncommitted governance edits, and finds a moved file through git rename detection and the mapping table (T1). Each drift is classified. **Content** (requirement or context text) is the owner's authority: it is shown, re-pinned on confirmation, and given a change record, never reverted silently. **Structure** (a moved file, a missing index row, a broken format, an unclosed fence) is repaired to the template structure with the content kept. **State that a gate reads** (a ticket state row, a review verdict, a dispatch digest, a receipt) is never accepted when edited by hand: it is restored from the pinned commit, or the flow step is run again. Every pin records the commit at which its leaf was last correct, so the restore source is git history, not a guess. Nothing is applied without the user's choice, except that hand-edited gate state is reported as not counting. **A restore is conservative.** Before it, the check confirms:<br>(1) the restore source is trustworthy, meaning its pin traces to an approval record;<br>(2) no approved commit after the pin changed the file; if one did, the pin is stale and is re-pinned, not restored;<br>(3) which files and passages would change, shown in plain language beforehand;<br>(4) the user agrees, file by file, with no one-click repair of everything.<br>A restore is a new commit, and the current version is kept beside it, so the restore can be undone. For a content edit the default proposal is to accept it; restoring needs the user's explicit choice after the preview. |
| T8 | Decision questions in business terms | Every question the harness puts to the owner states, for each option, what the user gets, what it costs in time and money, the risk, and whether it can be undone, in plain words. Technical detail (hashes, refs, workflow names) goes below the plain answer, never in place of it. The wording rules are the same rule set as T4's plain-language reports. |
| T9 | Install and update without a terminal | A user installs, updates and removes the plugin from the host's own interface (marketplace, plugin settings), and binds it to one project without typing commands. A wrong scope (the plugin enabled in a project the user did not mean) is found and reported in plain words. |
| T10 | Acceptance by seeing the product | Before a user accepts a change, the harness shows the working result in a form the user can open and try: a preview, a demo page, screenshots or a short recording, with what was checked stated in plain words. Receipts, test cells and CI stay as the evidence behind it. |
| T11 | Intake in plain language | The first stage asks for the goal, who approves, and how far the project should go, in everyday words. The terms Profile, POC, MVP and authority are mapped from the answers, and shown to the user only together with what they mean. |
| T12 | Every rule names what guarantees it | Each rule of `AGENTS.md`, `Workflow.md` and `CodeReview.md` is listed with the mechanism that holds it whether or not an agent remembers it: a gate (a program that refuses the result), a hook (the host blocks or records the action as it happens), or an independent review that reruns the evidence. A rule with none of these is either given one or listed as an open risk, in plain words. Written text alone is never counted as a guarantee. The inventory is a committed file, pinned like an index (T3), and the health check (T4) reports its open risks. |
| T13 | The full suite runs where it pays | A seat runs the tests its change touches (P1), not the full suite. The full suite runs in CI, on Linux and Windows, and once at integration. Every rule, template and dispatch line that requires a seat's F1 cell is changed to match, so the control plane never dispatches against its own rules. |
| T14 | The tier is computed from the boundary | A script reads a ticket's `johnny-boundary` block and computes its tier from the paths it changes. Records only, README or `doc/`: light. Governance text (the rule-bearing files that `specification-ticketing.md` lists as strict): governance. Code, gate scripts or tests: strict. Each tier names the cells a dispatch must carry. Dispatch lint refuses a dispatch whose cells do not match the computed tier, and refuses a ticket whose written tier differs from the computed one. |
| T15 | Every ticket has its rule-only review before dispatch | Every ticket, of every tier, has an independent rule-only review before dispatch. Today only strict tickets do (`specification-ticketing.md`, rule-process-tier). Dispatch lint refuses a dispatch when no ticket-review record covers the ticket's current revision. A revision that applies the reviewer's exact fixes counts as covered. |
| T16 | The control plane's own steps have gates | The control plane's work is checked by programs, as a seat's is. (1) A ticket's "after integration, control-plane work" list becomes a machine-readable block, like `johnny-boundary`. Each step names the evidence that closes it: a commit, a CI run or a file. The integration script does not mark a ticket `INTEGRATED` while a step has no evidence, and the health check (T4) lists the open steps in plain words. (2) An inventory is produced by a program from its source and compared with any hand-written list, never written by hand alone. (3) A consistency script compares a ticket's revision in its state and binding rows, its dispatch digest, its index row and its review records, and refuses a mismatch. |
| T17 | Progress and waiting time in plain words | The user sees what the AI is doing now, how long it usually takes, and whether the user must act. (1) A seat writes a timestamped line to its out directory when each cell starts and ends; the record is evidence as well. (2) A status command reads the state and these lines and prints, in plain words, the ticket, the current step, the time elapsed, the usual range for that step, the next step, and one of "you need do nothing", "a decision is waiting for you", or "a test is waiting for you". (3) The usual ranges come from recorded history per tier and step (median to 90th percentile), the same data as the dispatch-to-integration time of the carried lessons. (4) The user is notified when a step ends or a decision waits, not asked to watch. The wording follows T8's rule set. |
| T18 | The harness proves its value with measured data | Three measurements decide how far the harness is kept. (1) **Small-ticket cost after T13 to T15**: for each ticket, the time from dispatch to integration, the rounds and the processed tokens, by tier, taken by `rework_report.py` and `usage_report.py`; the aim is a small change in one to two hours instead of a day (wave 3 baseline: ticket 82, a hook and README paragraphs, eight revisions in about one day). (2) **Real feature tickets in a target project the owner uses**: two to three feature tickets, each recorded with dispatch-to-integration time, rework rounds and the defects found after integration, compared with the same project's recent work done without the harness; the target project is named only in that project's own records, never in this repository. (3) **An install by someone other than the owner**: the installer follows `doc/runbooks/install-guide-0.5.0.md` alone and reports each step and problem; success is a working install with no help from the owner. The result is a written verdict with the numbers. If small tickets stay slow or the review finds too few defects to pay for its cost, the harness is cut down to three cores: state in files, independent review that reruns the evidence, and the rules that matter held by a gate or a hook. |
