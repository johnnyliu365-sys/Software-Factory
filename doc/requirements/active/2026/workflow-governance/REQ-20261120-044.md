## Why

Wave 3 made the gates real at the level of one ticket: dispatch lint, evidence gate, usage report, integration script. Around a ticket, the harness still relies on an agent reading rules and following them:

- **Where the documents live, and how they get there.** In a new project an agent copies them from the template; in a mature project it should reuse the project's own paths; in a half-built project old and new copies are mixed. Nothing checks which case applies.
- **Indexes are not pinned.** `index_pins.py` exists, but no index in a target project carries its pin format, no hook runs it, and CI does not run it.
- **A user who is not an engineer cannot see where the mechanism failed.** On 2026-11-20 the owner saw Codex, with the 0.4.14 plugin installed, answer a plain lookup by reading `Workflow.md` and the whole governance chain. The owner saw it because the owner designed the harness; a lay user sees only slowness or odd behaviour. Ticket 79 fixes the entry for 0.5.0. Copies of `AGENTS.md` and `Workflow.md` already in target projects keep the old rule.
- **Agile coupling outlives the POC.** The harness allows a fast, agile POC, but nothing stops the coupling of a POC from becoming the architecture of the product. Module boundaries exist only as an architecture document; no gate compares the code with them. The language policy fixes one backend language but does not require the choice to be made against the project's needs, nor its trade-offs and technical debt to be stated before the choice.

## Themes

| # | Theme | What it delivers |
| --- | --- | --- |
| T1 | Project-type survey and mapping | A program surveys the document tree and writes a versioned survey record. For each standard source (CONTEXT, PRD, requirements, SPEC, tickets, reviews, ADR, handoffs, state files) the record holds the path, missing or in conflict. The project type (new, mature, half-built) follows from signals in that record, not from an agent's impression. A mature or half-built project gets a versioned mapping table (standard source → this project's path), and every later check and hook finds files through it. Each type sets its baseline: empty for a new project, the surveyed state for the other two. The classification states its evidence and a confidence level. A mature project can have no governance documents at all, so structure alone does not decide. When the evidence is insufficient, the type is `PENDING_OWNER`; the owner decides, and until then no document is created and no structural repair is applied. |
| T2 | Old copies of the plugin's rules | The copies of `AGENTS.md` and `Workflow.md` a project holds carry a version marker. At the start of a session the entry compares them with the installed plugin, and reports an older copy with the way to update it instead of following it. |
| T3 | Index pins and the hook loop | Target-project indexes use the pin format of `index_pins.py`, kept by `--write`. A post-edit hook runs `--check` when a leaf or an index under the mapped paths changes, and a pre-commit hook blocks drift. Both find their scripts and files from the project root the host passes (`CLAUDE_PROJECT_DIR`), never the working directory, and block only the action they check (L-23 addendum of 2026-11-19). A digest over a fenced block fails on an unclosed fence, and a digest that did not change after its content changed is flagged (2026-11-19 lesson). CI runs the same checks as the backstop. **Limits stated:** the plugin installs no git hook in a target project, and CI checks only when it runs. T3 proves integrity, meaning that controlled content has not changed without approval. It does not prove that the content is correct or that an agent understood the requirement; that is the work of independent review and behaviour gates. A pin baseline edited together with its leaf would make the check agree with itself, so every change of a pin value must trace to an approval record (a ticket or a change record), and CI checks the history for pin changes without one. A preflight sweep clears the stale residue of a seat that has ended, judged by run id and age, and records it (external review, 2026-11-19). |
| T4 | Self-diagnosis in plain language | A health-check command, run by the user or at session start, reports in fixed plain-language form what is wrong, what it means and what to do. It covers the survey state, old copies, pin drift, stuck tickets and the last halt. Every halt code has a shipped plain-language entry (L-16). A hook records which files an agent read, and flags a behaviour that breaks the routing, for example a read-only lookup that read `Workflow.md` or many governance files. **Strictness the user feels as protection (owner direction 2026-11-26).** (a) Every message that stops or refuses something has four parts in plain words: what was stopped, what that protects the user from, what the user has to do (one step, or "nothing"), and how to go on if the user insists; a lint checks the four parts, and a code such as `EXIT_MISMATCH` goes below them, never in their place. A check that fails silently (a hook that did not run) is itself reported this way. (b) A ledger of what was stopped: one plain line for each catch, with when it was caught and what it would have reached (for example "before release: the README said more than the test showed"), which the user can read at any time. (c) The README says whom the gates govern: they check the AI on the user's behalf, and the user decides. (d) **The form of a command says whether it may run now.** A command is shown in a form that runs at one click only when it can be run at that moment: every condition it waits for holds, and the agent has checked each one just before showing it. A command that must wait (a test run that is not finished, a commit that does not exist yet, an earlier step not done) is shown in a copy-only form, with the condition it waits for, and is shown again in the runnable form once the condition holds. The two forms are never mixed in one block. The decision still shows the effect and the rehearsal's evidence in plain words first, each runnable command is labelled as the real action and works from any directory, and a rehearsal's output and the real output are told apart at their first line ("rehearsal, nothing was changed"), because `git push --dry-run` prints the same line as a real push. Who runs a ready command follows the user's profile, as in rule (e): an engineer may press it themself, and the agent then reads the result back from the system, not from pasted output; for a user who is not an engineer, the command stays plain text, the user confirms in words by one path only, and the agent runs it. The incident of 2026-11-26 was a command that was not yet ready (the tests were still running) shown in the runnable form; the fault was the form not matching the state, not the button. The two forms work as a signal only while they are used truthfully and the runnable one stays rare: the owner's reason for the rule is that it makes the user read the command before pressing. So each runnable block is preceded by one line naming what to check in it (the target branch, the commit id, the repository), with the values written out, never a placeholder. (e) **A protection does not move its cost to the user.** A check the user would have to switch on, wait for or switch off by hand (a branch-protection setting, for example) is felt as obstruction; the same check belongs in the agent's own step: the release script reads the commit's CI result itself and refuses the push until it is green, issues a one-time confirmation code at the rehearsal, and runs the real push only with that code. The test of rule (e) is what the user must know: a protection may not require the user to know its mechanism. The owner's reason, in the owner's words: "如果站在工程師角度,我會選擇直接用CI擋／但是PM根本不知道什麼是CI,這就是我說不開的原因". So the same check has two forms by the user's profile: for an engineer, the host's own block (required CI checks on the default branch) may be offered as an option; for a user who is not an engineer, the agent holds the check in its own step and says in plain words what it is waiting for and for how long ("the automatic tests are still running, about ten minutes; I push when they pass"), and the word CI is not needed to follow it. |
| T5 | Module boundaries after the POC | The POC may be agile. To leave the POC, two things are required: a module boundary map (each module's responsibility, public interface and allowed dependencies) and a technical-debt inventory of the POC's couplings, kept in the per-feature record of existing design and known debt (L-21). From MVP on, a dependency-rule gate compares the real import graph with the map at every integration. A new forbidden edge or a cycle is red, and fan-in and fan-out are reported. |
| T6 | Technology choice with its trade-offs stated | Before the POC ends, architecture produces a decision record that compares candidate backend languages and frameworks against the project's needs. The needs it covers are target users and scale, traffic and latency, front-end responsiveness, deployment and running cost, and team maintainability. The record states each option's strengths, weaknesses and the technical debt it brings. The owner approves it, and the choice is then fixed; a later change goes through change control. The language gate becomes mandatory from MVP on, instead of at a stage the target project picks. |
| T7 | The user's own edits: detect, classify, restore | Hooks see only an agent's actions. A user who edits, moves or deletes a governance file in an editor bypasses them, and the plugin may not become a target-project git hook. The session-start health check (T4) therefore compares the index pins (T3) with the tree, lists uncommitted governance edits, and finds a moved file through git rename detection and the mapping table (T1). Each drift is classified. **Content** (requirement or context text) is the owner's authority: it is shown, re-pinned on confirmation, and given a change record, never reverted silently. **Structure** (a moved file, a missing index row, a broken format, an unclosed fence) is repaired to the template structure with the content kept. **State that a gate reads** (a ticket state row, a review verdict, a dispatch digest, a receipt) is never accepted when edited by hand: it is restored from the pinned commit, or the flow step is run again. Every pin records the commit at which its leaf was last correct, so the restore source is git history, not a guess. Nothing is applied without the user's choice, except that hand-edited gate state is reported as not counting. **A restore is conservative.** Before it, the check confirms:<br>(1) the restore source is trustworthy, meaning its pin traces to an approval record;<br>(2) no approved commit after the pin changed the file; if one did, the pin is stale and is re-pinned, not restored;<br>(3) which files and passages would change, shown in plain language beforehand;<br>(4) the user agrees, file by file, with no one-click repair of everything.<br>A restore is a new commit, and the current version is kept beside it, so the restore can be undone. For a content edit the default proposal is to accept it; restoring needs the user's explicit choice after the preview. |
| T8 | Decision questions in business terms | Every question the harness puts to the owner states, for each option, what the user gets, what it costs in time and money, the risk, and whether it can be undone, in plain words. Technical detail (hashes, refs, workflow names) goes below the plain answer, never in place of it. The wording rules are the same rule set as T4's plain-language reports. Each question also draws the three points a translation needs (T21 rule (0)): what the user will see when it is done, what must not happen, and why it is wanted. Each option states the first two for itself, so choosing it confirms them. When the user's request leaves one of the three open, the question asks for that one point, with a proposed answer the user can accept or correct; it never hands the user a form to fill in. The answer is recorded verbatim beside the choice, and the read-back and the first tests are checked against it. |
| T9 | Install and update without a terminal | A user installs, updates and removes the plugin from the host's own interface (marketplace, plugin settings), and binds it to one project without typing commands. A wrong scope (the plugin enabled in a project the user did not mean) is found and reported in plain words. **The measure is what the user already does (owner, 2026-11-27).** A user who is not an engineer types in a chat box, presses "allow" and presses "install" in an app; a terminal is a wall they do not cross, however short the command. So there are two targets, and a command line is neither of them. (1) **Listed in the host's own directory**: the user presses install in the app. This needs the listing to be applied for and kept up, and it also serves a company that installs for its staff, so a separate administrator path is not planned. (2) **One sentence in the chat**: the user asks the AI they already use to install the plugin, and the AI runs one fixed installer script that the plugin ships; the user only allows the command. The script, not the AI's own judgment, finds a usable host command and checks its version, adds the marketplace, installs, removes an old plugin with the host's own removal commands, checks that the hook runs, and prints each result and the next step in plain words. The same script is the first form of the health check (T4). An AI that improvises install or cleanup commands is the failure this prevents: in the first outside install a session was given two delete commands for cache folders, one of them for a path that does not exist. (3) **Codex without a terminal.** The Codex desktop app does not ask whether to trust a plugin's hook; today only the terminal does, and the answer must be the user's own. So on Codex the installer may, after the user says yes in the chat, add one marked line to Codex's global instruction file that names the plugin's rules file and the first step of a lookup (owner decision 2026-11-27, which changes the decision of 2026-11-26 in the carried row on T4). The conditions answer the three reasons of that earlier decision: the line is written and removed only by the installer script, which the AI runs, so an install can now run a script; the line carries a begin and an end marker and no version in its path, or is rewritten by the same script on every update and removed on uninstall, so nothing stale is left; and it goes into the instruction file the user owns, never into the host's own memory files, which the host rewrites. The exact line is shown to the user before it is written, the yes is asked again at each install, update and removal, and the health check reports whether the line is there and whether the hook runs. (4) The terminal commands stay as the engineer's path and as what the script itself runs. |
| T10 | Acceptance by seeing the product | Before a user accepts a change, the harness shows the working result in a form the user can open and try: a preview, a demo page, screenshots or a short recording, with what was checked stated in plain words. Receipts, test cells and CI stay as the evidence behind it. |
| T11 | Intake in plain language | The first stage asks for the goal, who approves, and how far the project should go, in everyday words. The terms Profile, POC, MVP and authority are mapped from the answers, and shown to the user only together with what they mean. |
| T12 | Every rule names what guarantees it | Each rule of `AGENTS.md`, `Workflow.md` and `CodeReview.md` is listed with the mechanism that holds it whether or not an agent remembers it: a gate (a program that refuses the result), a hook (the host blocks or records the action as it happens), or an independent review that reruns the evidence. A rule with none of these is either given one or listed as an open risk, in plain words. Written text alone is never counted as a guarantee. The inventory is a committed file, pinned like an index (T3), and the health check (T4) reports its open risks. |
| T13 | The full suite runs where it pays | A seat runs the tests its change touches (P1), not the full suite. The full suite runs in CI, on Linux and Windows, and once at integration. Every rule, template and dispatch line that requires a seat's F1 cell is changed to match, so the control plane never dispatches against its own rules. **A cell is bound to its inputs, not to the commit (owner decision 2026-11-27).** Today every cell of a receipt must name the last commit, so a correction that deletes one test line reruns everything (ticket 77 revision06: the parity run, the full suite and CI again, about an hour, for a one-line change to a test). The rule becomes the one a build system uses: each cell declares its inputs (files, the command, the tool versions it reads), the receipt records the digest of those inputs with the cell's result, and a cell whose input digest is unchanged at the new commit is carried over, marked as carried with the commit it ran at; it is not rerun. (1) The inputs are computed by a program, never written from judgment: a test cell's inputs come from the import graph of the test files it names, a script cell's from the paths the cell declares and the gate confirms it read. A cell whose inputs cannot be computed is rerun every time. (2) An under-declared input is the risk (a stale pass is carried), and the harness has no sandbox to prevent it, so two backstops stay whole: CI on the remote runs every test at every commit, on both systems, with no carry-over, and the reviewer reruns what it chooses without regard to the carried marks. A carried cell is a saving for the seat, never evidence for the reviewer. (3) The evidence gate checks the carry: it recomputes each carried cell's input digest at the candidate and refuses a mismatch. (4) The time and tokens of ticket 77 revision06's correction round are the baseline this is compared with (T18). |
| T14 | The tier is computed from the boundary | A script reads a ticket's `johnny-boundary` block and computes its tier from the paths it changes. Records only, README or `doc/`: light. Governance text (the rule-bearing files that `specification-ticketing.md` lists as strict): governance. Code, gate scripts or tests: strict. Each tier names the cells a dispatch must carry. Dispatch lint refuses a dispatch whose cells do not match the computed tier, and refuses a ticket whose written tier differs from the computed one. |
| T15 | Every ticket has its rule-only review before dispatch | Every ticket, of every tier, has an independent rule-only review before dispatch. Today only strict tickets do (`specification-ticketing.md`, rule-process-tier). Dispatch lint refuses a dispatch when no ticket-review record covers the ticket's current revision. A revision that applies the reviewer's exact fixes counts as covered. |
| T16 | The control plane's own steps have gates | The control plane's work is checked by programs, as a seat's is. (1) A ticket's "after integration, control-plane work" list becomes a machine-readable block, like `johnny-boundary`. Each step names the evidence that closes it: a commit, a CI run or a file. The integration script does not mark a ticket `INTEGRATED` while a step has no evidence, and the health check (T4) lists the open steps in plain words. (2) An inventory is produced by a program from its source and compared with any hand-written list, never written by hand alone. (3) A consistency script compares a ticket's revision in its state and binding rows, its dispatch digest, its index row and its review records, and refuses a mismatch. |
| T17 | Progress and waiting time in plain words | The user sees what the AI is doing now, how long it usually takes, and whether the user must act. (1) A seat writes a timestamped line to its out directory when each cell starts and ends; the record is evidence as well. (2) A status command reads the state and these lines and prints, in plain words, the ticket, the current step, the time elapsed, the usual range for that step, the next step, and one of "you need do nothing", "a decision is waiting for you", or "a test is waiting for you". (3) The usual ranges come from recorded history per tier and step (median to 90th percentile), the same data as the dispatch-to-integration time of the carried lessons. (4) The user is notified when a step ends or a decision waits, not asked to watch. The wording follows T8's rule set. The number of times a ticket asked the user to act, and how long the user waited, are recorded per ticket; the aim is that the user is interrupted only for a decision. A stop comes as early as it can: before dispatch (T21 rule (0)) and not after the work is done. |
| T18 | The harness proves its value with measured data | Three measurements decide how far the harness is kept. (1) **Small-ticket cost after T13 to T15**: for each ticket, the time from dispatch to integration, the rounds and the processed tokens, by tier, taken by `rework_report.py` and `usage_report.py`; the aim is a small change in one to two hours instead of a day (wave 3 baseline: ticket 82, a hook and README paragraphs, eight revisions in about one day). (2) **Real feature tickets in a target project the owner uses**: two to three feature tickets, each recorded with dispatch-to-integration time, rework rounds and the defects found after integration, compared with the same project's recent work done without the harness; the target project is named only in that project's own records, never in this repository. (3) **An install by someone other than the owner**: the installer follows `doc/runbooks/install-guide-0.5.0.md` alone and reports each step and problem; success is a working install with no help from the owner. (4) **The implementation seat's model tier**: wave 3 ran every implementation seat on one tier (`claude-sonnet-5-5`, effort high), so the effect of a higher tier on the first-pass rate is not measured. What is measured, with the model fixed: of the 6 tickets dispatched without a rule-only review none passed its first code review, and of the 11 dispatched with one, 6 did; 11 of 17 tickets had at least one implementation-side cause (`IMPLEMENTATION_DETAIL` or `RETURN_UNTRUE`, 16 of 26 causes), which is the most a perfect implementer could remove. In wave 4, tickets of the same tier alternate between the two model tiers for the implementation seat, and each records first pass or not, the cause kinds, tokens and time; the default tier is decided after 8 to 10 tickets on each side, and looked at again once T20 is in use, because the runner removes procedural slips whatever the model. Until then the model follows difficulty, as `doc/runbooks/dispatch-model-profile.md` already says: a ticket with no precedent in the repository (ticket 77's acceptance script took five rounds) is dispatched one tier higher, and a ticket that follows an existing pattern stays on the current tier. (5) **False stops**: every stop by a gate, hook or lint is marked afterwards as a real problem or a false stop, and the rate is reported per gate; a gate with many false stops is fixed or lowered to a warning (one seen on 2026-11-26: dispatch lint R5 took a semicolon inside a parenthesis for two actions). Strictness follows risk (T14), so the rate is read per tier. The result is a written verdict with the numbers. If small tickets stay slow or the review finds too few defects to pay for its cost, the harness is cut down to four cores: state in files, independent review that reruns the evidence, the rules that matter held by a gate or a hook, and translation fidelity (T21). **First data for measurement (3), 2026-11-27.** One outside installer, on Windows with only the Microsoft Store version of the Codex desktop app and an old plugin installed, did not get through on the guide alone. Eight obstacles in about an hour and about twelve exchanges relayed by the owner: the `codex` command was not on `PATH`; the copy inside the app's folder was refused by Windows; another copy was too old to have `plugin add`; the usable copy sat in a folder with a generated name; the interactive screen needed `--no-daemon`; the trust question did not appear at the first try; someone had been given delete commands for cache folders in place of the removal commands; and `codex plugin list --json`, which the guide itself names, did not return. The install ended registered, with the old plugin removed and the hook's trust recorded. The result counts as failed for (3) and moves T9 forward. |
| T19 | Less context per call, and less natural language between agents | A seat's cost is the context it carries times the number of model calls. Measured on ticket 82 (three rounds by resumption): the implementation seat made 189 calls, its context grew from about 52,000 tokens at the first call to about 322,000 at the last, and the calls sum to 39.9 million processed tokens; the review seat made 117 calls, from about 52,000 to about 332,000, 24.3 million in all. Of the tool output a seat read, piecemeal `cat`/`sed`/`grep` was 58% (implementation) and 46% (review), `git diff`/`show`/`log` 24% and 36%, the ticket leaf about 10%, test output about 5%; the dispatch file is read once and is small. The levers, largest first: (1) **resume or start fresh by a water mark**, decided by a script and not by memory: it reads the context of the seat's last call from the host transcript and the size class the dispatch states, and prints RESUME or FRESH. Both costs are the context per call times the calls; a resumed seat carries the earlier rounds and needs fewer calls, and a fresh seat starts at about 52,000 tokens and spends calls on reading the background (27 more calls in the one measurement). The starting marks, from ticket 82 only, are the carried context above which a fresh seat is cheaper: about 300,000 tokens for a small fix (up to about 10 calls), about 190,000 for a delta round (about 30 calls), and about 130,000 to 150,000 for a full round (50 calls or more); the call counts per class are the control plane's estimate. A seat that has done one full round stands at about 190,000 tokens, so the next round starts fresh unless it is a small fix. Three things beside the token count favour a fresh seat: rounds are hours apart, so a resumed seat's whole context is written to the cache again; a resumed seat still holds earlier revisions' instructions; and a fresh reviewer is not anchored on its own earlier approvals. A small fix favours resuming, and so does a pitfall the seat has just met that the dispatch does not yet state. The marks are recalibrated from T18's data and again once T20 is in use, since a fresh seat then reads the bundle and not the history. A fresh seat starts from the dispatch, the previous receipt's path and the delta, instead of resuming a seat that carries every earlier round (first measured on ticket 82 revision08: a fresh review seat made 57 calls and processed 6.4 million tokens, against 30 calls and 9.2 million for the resumed seat's review of the same-sized revision06 delta, about 30% fewer tokens with almost twice the calls; the resumed implementation seat's fourth round started at about 302,000 tokens of context for a one-paragraph change); (2) **one command per group of cells**: a cell runner that runs the cells of a dispatch, writes each capture and prints one line per cell (exit and path), and a receipt builder that assembles the receipt from the captures, so a seat does not run and read them one by one; (3) **a smaller fixed overhead per call**: a seat agent type that carries only the tools a seat uses, with the saving measured at the first call; (4) **typed values in the dispatch**: paths, commits, commands and expected exits as values, and references to a ticket item by its number instead of a restatement in prose; (5) **the ticket leaf holds only the current content**: revision history moves to the review record and the state row holds the state and the digest; (6) **the receipt refers to captures** by path, digest and exit instead of embedding them, once the evidence gate reads them from the files. Agent-to-agent text stays in English and text for the user in Chinese. Measured 2026-11-26 by the owner's method (one ticket excerpt written both ways, read once by a fresh seat on `claude-sonnet-5-5` and on `claude-opus-5-5`, identical counts on both): the English version is 2,535 characters and about 933 tokens, the Chinese version 1,513 characters and about 1,079 tokens, after subtracting a control read of 2,268 tokens; Chinese costs about 15% more for ticket text whose paths, ids and quotations are the same in both. Projected on ticket 82's implementation seat (about 50,000 characters of natural-language input, 189 calls), writing it in Chinese would add about 0.5 million tokens, 1.3% of that seat's total: the rule is right and the lever is small. The fixed context of a call was measured the same day with a one-line prompt: 50,451 tokens for the general-purpose seat type and 34,035 for the read-only search type. At 50,451 tokens, the fixed part is about 24% of each ticket 82 seat's total (189 and 117 calls), so lever (3) is worth a seat type of its own; its saving beyond the 16,000 tokens already seen is measured before it is built. The first tool call of a seat carried about 2,268 tokens beyond the file content; whether every call carries that is not yet measured. T18 measurement (1) gains, per seat, the number of calls, the context at the first and last call and what filled it. |
| T20 | A ticket is an executable spec bundle, not prose | What one agent hands another is code and data, and natural language is kept for the owner. A ticket's machine part is a spec bundle: (1) a manifest with typed values (ticket id and revision, base commit, branch, boundary globs, tier, and for each cell its argv, expected exit and capture path); (2) each fixed text of the ticket (a README paragraph, a hook command) as its own data file, named by path and digest and never restated; (3) the acceptance tests, written before dispatch and failing at the base, which the seat makes pass and may not change; (4) each mutation as a patch file with the test it must turn red. A runner executes the bundle: it checks the worktree, runs the cells, applies each mutation in a disposable clone, and builds the receipt; the seat's instruction is a fixed template of about ten lines. A dispatch rule that a gate or hook already enforces (other branches, `Any`, paths outside the boundary) is not written again. Natural language remains in three places: the owner's decision, quoted verbatim at the head of the bundle; work that needs judgment and has no acceptance test yet; and a seat's report of something unexpected. The rule-only review judges whether the tests and data files encode the owner's words, so the words are translated once and reviewed once. The bundle lies outside the seat's writable boundary and its digest is on the ticket's state row, so a seat cannot pass by changing the spec. This theme carries T19 levers (2) and (4). |
| T21 | Translation fidelity is a core module: A_N equals A_0 by construction, and drift is counted | Every natural-language hop can change the meaning, and the first hop already does. Counted on wave 3: of 24 rule-only reviews, each of one hop (the owner's words or an owner test, written as a ticket by the control plane), 22 returned `CHANGES_REQUESTED`, with 222 findings in all; none of the 11 tickets passed its first rule-only review. The findings are not all changes of meaning: in ticket 82, by the control plane's own unreviewed sorting, about 7 of 29 changed the meaning and the rest were omissions or stale restatements, so the count shows first that a specification in prose is never complete. Drift has three kinds: (a) the meaning changed, or the text says more than the evidence; (b) something is left out or undecidable, so the receiver guesses; (c) the source changed and a restatement elsewhere did not, which grows with the number of copies, not hops. The module holds five rules. (0) **A read-back before any dispatch**: the two hops that carry the most risk lie before the first test, namely the owner's meaning against the option text the control plane wrote (most owner decisions choose among options the control plane worded), and the owner's words against the first tests. A byte copy keeps an error of these hops intact, and the owner's rule is that a misunderstanding here is amplified by every later step ("理解錯誤,後面的浪費會指數級放大"). Stated exactly: the later a misunderstanding is found, the more is wasted; the waste is about the work already built on it, so it accumulates stage by stage, and it steps up at each point that cannot be undone (a release, anything outward). It multiplies only where the misunderstanding becomes a base that other work depends on (an architecture, a data model, a published version). One observed pair in wave 3: a sentence that said more than the evidence was caught at the rule-only review and fixed in minutes; a host behaviour that was misunderstood was found after integration and cost a reopened ticket and about three hours. Acceptance by seeing the product (T10) is the same check at the end. (1) **One hop in natural language**: the owner's words, quoted verbatim, become tests and data files (T20) once, and that hop is reviewed against the quotation. (2) **Byte copies after it**: every later hand-over names a path and a digest, so equality is checked by a program and not by reading. (3) **One home for each fact**: other places refer to it by path and item number and do not restate it; a lint refuses a restated value where a reference exists (a commit id, a fixed text, a rollback target). The module stays small: its code is the read-back generator, one lint and one counter in the report; rules (1) and (2) are T20's design, not a system of their own. |
| T22 | A change goes to the ticket that owns the feature, and a guard is counted only if it can refuse | A requirement change or an extension belongs to the ticket that owns the feature; a new ticket number is for a feature no ticket owns. (1) **Ownership map.** Each ticket declares what it owns in a machine-readable block (the feature name, and the paths of its `johnny-boundary`); a script builds the map feature to owning ticket from the tickets, so the map has one home (T21 rule (2)) and is pinned like an index (T3). The map also lists, per feature, the owner decisions that are settled, each with its date and its row. (2) **The gate watches the outcome, not the tool.** At commit and again at integration, a script reads the diff. A ticket leaf that the diff adds must carry an ownership-lookup block: the script's own list of candidate owners (tickets whose boundary paths or feature names overlap the new ticket's), and for each candidate one line saying why it does not own this work. A missing block, or a candidate left without a reason, refuses the commit. The agent does not answer the question "does an existing ticket own this" from memory; the script prints the candidates. (3) **Reopening is a listed transition.** A change to a feature whose ticket is `INTEGRATED` reopens that ticket as a new closure revision, with its own initial review. Today `specification-ticketing.md` lists no transition out of `INTEGRATED` and `CodeReview.md` §4 names only a follow-up `PLANNED` ticket, so tickets 82 and 77 were each reopened by an owner override; the rule is written so that the override is no longer needed, and the reason for reopening is a field of the revision. (4) **A ticket cites the decisions it rests on.** A ticket's scope and its risk tier name the settled decision rows of the map they depend on. The read-back before dispatch (T21 rule (0)) repeats them, and the rule-only review (T15) checks the ticket against them, so a settled decision is not restated wrongly and the owner does not say it twice. (5) **What counts as a guard (extends T12).** The rule inventory records, for each guard, its mode (refuses or only warns), the event it watches, and the routes it covers (the host's write tool, a shell write, a commit). Four shapes are counted as no guard and reported by the health check (T4) as open risks: a text reminder shown on every event, however often it is shown; a check in warn mode; a check that runs after the change and only reports; a hook bound to one tool when another route writes the same file. A check that is green on a different question (the new ticket's index row exists) is not evidence for this one (the new ticket should not exist). A note in the agent's memory is text, and is never the remedy for a rule that a mechanism was meant to hold: the remedy is to find why the mechanism did not refuse. (6) **Where the map is consulted.** "Before a ticket is opened" is the right time to look, but it is not an event a program can see: a hook before a write is bound to one tool, which is shape four of (5). So the lookup is tied to artifacts and events that exist whichever way the files are written, at four points. (a) **When a requirement or a change comes in**, at change control and before any ticket text: the lookup script is run on the request, and its result (the owning ticket and "reopen", or "no owner, new ticket", with the settled decisions of that feature) is a field of the change record. This is the earliest and cheapest point, and the one the lookup is designed for. (b) **At the read-back before dispatch** (T21 rule (0)): the plain-language read-back shows that field in one line, so the owner sees "this reopens ticket N" or "this is a new ticket, because no ticket owns it" before any work starts. (c) **At commit**: the refusing gate of (2). It recomputes the candidates and compares them with the block, so a block written by hand or against an older map is refused. (d) **At integration**: the same check again, because a commit hook can be skipped or absent on another machine. The map itself is rebuilt and its pin checked (T3) whenever a ticket's ownership block changes, so no lookup reads a stale map. The same gate covers the opposite error: a ticket revision whose boundary grows into paths another ticket owns must name that ticket and the reason. (7) **Several requirement lines, several sessions.** When one product is worked on by several sessions, each on its own requirement line, ownership is declared where the work is and collected by a program; no session writes a central map by hand, and no session is the only one allowed to open tickets. (a) **Three layers, one home.** A ticket declares the feature, the paths and the requirement line it belongs to. The line's map and the product map (all lines, with a column for the line) are both built from the tickets by the script of (1); neither is edited by hand, so two maps cannot disagree. (b) **A ticket is opened on the shared branch first.** Opening a ticket is a small commit pushed to the shared branch before any work starts. The product map is rebuilt at that commit, so the second of two sessions that claim the same feature, or overlapping paths, is refused within minutes at its push, not at an integration weeks later. Ticket numbers are allocated the same way: the first push takes the number and the later one renumbers. (c) **A change across lines is made by the line that owns the ticket.** When a request of line A touches a feature that a ticket of line B owns, the lookup names that ticket; line B reopens and changes it, and line A records a dependency on the new revision. The read-back before dispatch (6)(b) tells the owner so in one line, and the owner decides which session takes it. (d) **Every feature has an owning line.** A module that several lines use and none owns is extended by each of them; the product map refuses a feature without a line, and shared modules go to a named shared line. (e) **A session loads its own line's slice, and looks up against the product map.** The session-start hook injects the line's slice and the place of the product map, not the whole map (T19). The lookup script fetches the shared branch first and reads the product map there, so a session never decides ownership from the copy its branch started with. (f) **Overlapping paths of tickets in flight** on different lines are refused at dispatch, by the same map: one set of files has one writer at a time. (g) **The remote repository is the root.** The authority for every map and index is the shared branch on the remote, not a local checkout and not a session's memory of it. Two sessions that share one local checkout see each other's files only by accident of the disk; a session on another machine, in the cloud or on another host's clone sees nothing. So the scripts fetch the remote ref before they read or build, a map is authoritative only as committed there, and the refusing check also runs where no session can skip it (the remote's CI), because local hooks differ by host. When the governance documents live on a branch of their own, apart from the code, four more rules hold (owner, 2026-11-27, from a conflict between two sessions' proposals). (g1) **Pins are content ids, not commit ids.** A pin into the governance branch names what the content is (the file or tree id that git itself computes from content), so it is the same on every machine and branch and can be checked on the remote whether or not the history was pushed. A commit id is kept only where it names a commit of the code branch, whose history is pushed. (g2) **The code branch locks the governance snapshot it is checked against.** Code and tickets on two branches cannot share one commit, and a gate that reads the governance branch "as it is now" gives a different answer tomorrow. So the code branch holds one small lock file with the id of the governance snapshot, the gates read the ticket index at that snapshot and refuse when it cannot be read, and changing the lock is an ordinary reviewed commit. A gate is never repointed to the governance branch before that branch is on the remote and a fresh clone has shown that every file the gate reads is there. (g3) **The root covers the present state, not the history.** A governance branch pushed as snapshots is the root for what is true now; who changed what and when stays in the history, which is then on one disk. Backing up that history is a separate decision with its own means (a private bundle, for example), and the history is not rewritten to make it fit a push. (g4) **A file that cannot go to the remote leaves a tombstone, and no gate depends on it.** A file left out for its size or for personal data is listed in the snapshot with its path, its content id and the reason, so that a check tells "left out on purpose" from "missing". A ticket that holds personal data is published with that data redacted, not left out, because a gate cannot depend on a file the remote does not have. And one value has one home across the two branches as well: a test does not read its threshold from a ticket's prose, and when the value moves into the code the ticket cites the code's constant and does not repeat it (T21 rule (3)). (h) **Adoption in a project that already has tickets**, in this order. First the declaration format is fixed once, and the second line takes the first line's format instead of making its own. Then each line adds the declaration to its own tickets that are already settled; a line does not declare for another line's tickets. Only when every line has finished is the script written, by one named owner (it is a shared module under (d)), and from then on the script, not a session, keeps the product map. The script's first run is a report, not a repair: it lists features that two tickets claim, paths that overlap, tickets without a declaration and features without a line, and the owner decides each one; it never picks a winner by itself. Until the script exists, nothing refuses a double claim, so that period is kept short. The alternative, one coordinating session through which every ticket is opened, was not chosen: every line would queue behind it, each request to it would be one more natural-language hop (T21), and it stops all lines when it is closed or its context is full. |
